## PO-2026-07-30-SEC — a dated, expiring, ticket-owning per-advisory exception is not a fallback

**Directive (verbatim intent, PO, wave-2a lane brief).** "Solve honestly: check the ACTUAL
advisories today — pnpm overrides to patched minors where they exist; where an advisory is
genuinely unfixable upstream, use the scanner's documented per-advisory ignore WITH expiry date
+ ENG-3274 reference committed in-repo (a dated, visible, expiring exception is not a silent
fallback)."

**This SUPERSEDES the standing "no ignore-list" line taken on ENG-3274 on 2026-07-29** (that
comment says an `osv-scanner.toml` `IgnoredVulns` entry must never be added). The earlier line
was right about what it was refusing — a *silent, undated, unowned* suppression. It was wrong to
generalise that to every exception shape, because it left the only remaining "fix" as a
framework major migration of the client for an advisory whose fix the repo already carries.

**What was implemented, and why it is not a fail-open switch.** `osv-scanner.toml` at the repo
root carries exactly two `[[IgnoredVulns]]` entries, each with `ignoreUntil` and a `reason`
naming ENG-3274 and the tarball-level proof. `scripts/ci/audit-osv.sh` +
`scripts/ci/osv-gate.py` then treat that ledger as untrusted input and RED the build when an
entry has no `id` / `reason` / `ignoreUntil`, names no ENG ticket, has an `ignoreUntil` in the
past or more than 120 days out, is not a real TOML date, or — the ratchet — no longer matches a
reported advisory (a stale entry must be DELETED, not parked). The scan is run against a copy of
the lockfile in a scratch dir precisely so the scanner's own auto-discovery cannot filter the
excepted advisories out of the CI log: every finding, excepted or not, is printed.
`scripts/test/audit-osv-exceptions.spec.sh` (19 cases, hermetic, wired into the Security job)
proves each of those refusals, and validates the committed ledger itself.

**Legitimate case, stated once.** The only shape that may be excepted is an advisory-DATABASE
defect: upstream shipped the fix as a BACKPORT onto an older release line, the repo resolves that
patched backport, and the GHSA range was never SPLIT to exclude it. Not "inconvenient to
upgrade", not "unreachable in our app". Both current entries are that case and both are proven,
not argued.

## Correction of fact — react-router did NOT need a v8 client migration

ENG-3274 (and its 2026-07-29 comment) concluded the react-router HIGH could only be cleared by a
**react-router v8 client framework major migration**, on the evidence that `react-router-dom` has
no 8.x on npm. The first half of that is true; the conclusion was not. `react-router 7.18.2`
(published 2026-07-28, `react-router-dom@7.18.2` alongside it) carries the v7 BACKPORT of
GHSA-qwww-vcr4-c8h2 — its CHANGELOG entry is literally *"Harden RSC CSRF codepaths (#15353)"*.
The remediation was therefore a **patch bump inside the v7 line**, 7.18.0 -> 7.18.2, exactly
parallel to the brace-expansion backports the same ticket had already identified. The v8
migration is not required and is not scheduled. Lesson: when a GHSA names a single `patched`
version, check the maintenance lines' publish dates and changelogs too — an unsplit range hides
backports.

## PO-2026-07-30-FR30 — A-HARDENING is the home for post-activation upstream correctness fixes

**Problem.** PR #148 (crew/yafet) fixed a real white-screen defect — `userAtom` is null until the
user query resolves, and `user.settings?...` threw an uncaught TypeError that unmounted the whole
React tree — by adding null-guards to three UPSTREAM client files. That reds the FR-30 divergence
gate: the paths are on neither the frozen 13-row allow-list nor the ratified pre-existing
baseline.

**Call.** Admitted to `docs/runbooks/hardening-allowlist.json` as class `hardening` with real,
resolvable per-item anchors, and the count tripwire raised 15 -> 18 deliberately in
`scripts/dry-run-overlay-import.mjs` and its test. Reasoning:

- These are *correctness fixes to upstream behaviour* — the exact definition of the A-HARDENING
  class (ENG-2478) — and the anchor mechanism makes an upstream tag bump that breaks one fail
  loudly by name.
- They cannot move into additive fork surface: the deref is inside the upstream component. The
  gate's other remediation, "revert the edit", would re-break the product.
- The `preexistingDivergence` baseline was deliberately NOT used. It is defined as divergence
  that predates gate activation and may only shrink; recording new post-activation divergence
  there would mislabel new work as pre-existing. Raising a "pre-existing" list is the dishonest
  option even though it is the cheaper one.
- There is no client-side additive scope in the gate (`EXCLUDED_SCOPES` is server `orvex/**` and
  `packages/@orvex/**` only), so every client fix to an upstream file must land in a ledger. The
  15-item count was therefore always a tripwire against SILENT growth, not a permanent ceiling.

**Residue.** The A-HARDENING class is described as "verbatim per Architecture twQ3BBzpTE
section 2" with 15 named items; the ledger now carries 18. The architecture page needs a matching
amendment (wiki draft + human ratify) — tracked on ENG-3287, and stated in the ledger's own
`description` so the drift is visible in-repo rather than silent.
